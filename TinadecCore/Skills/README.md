# Skills resources

`ToolSkillResourceService` owns the shared and project catalog exposed at `/api/v1/tools/skills`. It implements both `IToolSkillResourceService` for Desktop management and `IToolSkillCatalog` for run admission. Shared resources are scoped to the active Core tenant and workspace; project resources have deterministic IDs derived from that scope, the persistent project ID and the relative skill path.

The catalog and Context module use `WorkspaceSkillDiscovery` and `WorkspaceSkillPolicy`. Invalid, unreadable, disabled and shadowed resources keep diagnostic metadata. Inherited selection prefers a same-name project resource. Explicit resource lists select exact IDs and refuse missing, invalid, disabled or invisible IDs; an empty list provides no skills.

Live shared source belongs to `IScopeStorageLocations.Skills`; project source is discovered only at `<project>/.tinadec/skills`. Scope `config` TOML documents are authoritative; the database is their projection. `StoragePaths.Root` denotes runtime data. Admission copies only enabled, selected packages into `packages/skills` or `packages/project-skills`; earlier runs retain those immutable versions. Only each selected package receives a read grant. There is no legacy root migration or discovery fallback.

Managed imports, edits and deletion use governed user actions, reviewed revisions, hashes and complete package manifests. Shared replacement removes old assets and restores old files if configuration persistence fails. Uninstall physically removes the live package and keeps retained versions for historical runs. Project replacement reviews every old asset so removed assets are deleted; uninstall prunes empty directories. Package paths reject links and traversal and enforce 256 files / 16 MiB limits.

All resource updates require revisions. Project content revisions fit the exact JavaScript integer range; provider file hashes remain the write precondition. Shared rows have optimistic concurrency and a unique live name per tenant/workspace. SQLite and PostgreSQL migrations are in the corresponding storage migration assemblies.

`MarketInstallService` requires the Core managed MCP registry. Registration never installs a program. Explicit pinned npm/PyPI installation is separately reviewed through `mcp_program_update`; versions belong to scope packages and receipts to scope state. Workspace snapshots include configuration and Skills source while excluding runtime storage. Source working directories remain separate from storage roots; free conversations default to `~/TinadecProjects`. See the [storage resource report](../../.tinadec_dev/reports/2026-10-09-storage-resources.zh-CN.md) for platform and MCP execution trust boundaries.
