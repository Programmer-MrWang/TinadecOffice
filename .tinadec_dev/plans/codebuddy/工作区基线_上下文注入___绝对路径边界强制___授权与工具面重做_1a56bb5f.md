## 问题背景
用户在桌面端"同意全部授权"后，模型仍回答"什么都没返回、不知道我的工作区在哪"。已用 live 库证据定位到的真实链路：

- 会话（项目 Jalium.UI，根 `C:\git\Jalium\Jalium.UI`）问"理解项目"，worker 是 `search` 模板，`tool_scope = ["mcp_search","mcp_invoke","read_file"]`。
- `mcp_search {"query":"项目"}` 返回 `{"results":[]}`（未配置任何 MCP server，且响应结构没有"为什么空"的字段）。
- 模型猜了个 `mcp_invoke {server_id:"filesystem", tool_name:"list_workspace"}` → 被判 mutating、只持有 `read:` 级 grant → `resource_access` 边界 `LevelDenied` → `explicit_deny`。
- 被拒后引擎直接判任务失败且从不写 `ResultJson`，模型连一条 Tool 消息都收不到 → 只能说"没有任何返回"。
- 结构性根因：`DmaEA/Prompts/Context` 全链路 `WorkspaceRoot|cwd|RootPath` 命中 0，工作区信息从不进入模型上下文，而工具却要模型自己给出路径。

## 产品概述
把"工作区"做成 TinadecOffice 的一等运行时概念：模型明确知道自己工作区的绝对根路径、路径契约与允许根边界；只读工具默认拿到工作区读权、写操作需写权加审批；任何失败、被拒、空结果都以结构化原因回灌给模型，使模型不再"什么都不知道"。

## 核心功能
- 工作区上下文进入模型提示：绝对根路径、是否 git 仓库与分支、顶层清单、路径契约说明
- 绝对路径契约与边界强制：路径必须落在允许根内，越界给出可执行、可读的报错
- 授权重做：默认工作区读权，写权与审批绑定，拒绝原因含根路径与缺失级别
- 工具面基线：内置文件、检索、只读 git 工具成为默认能力；MCP 作为可选扩展保留
- 结果可诊断：失败、被拒、空结果一律结构化回灌模型，并补齐工具描述与 MCP 诊断字段


## 技术栈
沿用既有栈，不引入新技术：.NET 10（TinadecCore 模块化单体 + TinadecTools 子进程，stdio JSON 行协议）、SQLite/EF Core、Vue 3 + TypeScript 桌面前端（仅改动 `GraphSeedPack/manifest.json` 与 pack bootstrap，不做 UI 工作）。

## 实施方案

### 一、核心策略
按"四条链"落地，每条链独立可验证，且都建立在既有扩展点上，不新造架构：

1. **工作区绑定冻结**：`AgentRuntimeConfigurationResolver.ResolveAsync(sessionId, ...)` 在准入时已经能拿到 session；通过既有 `IWorkspaceRootResolver`（`ProjectSessionStore`）解析出项目根，把工作区绑定（根绝对路径、额外只读根、是否 git 仓库/分支、顶层清单、路径契约）冻进 `FrozenRunConfigurationV1` 的新可选段。恢复路径**不重算**（与 Phase 2 的 `DeriveGraphTier` 纪律一致），但缺段时按既有"投影容错 vs 恢复门禁"惯例回落为无工作区（不新增 schema 门禁）。
2. **提示注入**：`PromptAssembler.AssembleAsync` 增加一个工作区块（与 mode profile / agent profile 同级、受同一 token 预算约束），文本采用 OpenCode `<env>` 与 Codex 提示的形态：绝对根路径、路径契约（绝对路径 + 必须落在根内）、git 与顶层清单、"不要向用户索要工作区路径"。
3. **边界强制**：工具侧 `WorkspacePathResolver` 从"单根 = 子进程 CWD"升级为"允许根集合（主根 + 额外只读根）"，接受绝对路径并逐段校验在集合内，越界抛结构化错误（含尝试路径与允许根）；写操作只允许主根。Core 侧 `ToolResourcePathRegistry` 扩到 `ls/stat/file_search/git_*/shell.cwd`，把绝对路径归一为 claim 路径，使 `resource_access` 真正带路径维度。
4. **可诊断回灌**：引擎在 `dispatch.Status != Completed` 分支为 `pendingTurn.ResultJson` 写入结构化错误 JSON（工具返回给模型的 Tool 消息），空结果由工具侧补 `reason/diagnostics`；`mcp_invoke` 不再因 `RequiresApproval` 被隐式判定为 mutating，种子包工具面与写权在**发布期**做一致性校验，从源头消灭"声明了 mutating 工具却没写权"的自相矛盾。

### 二、关键决策与取舍
- **路径契约取 Codex 式绝对路径**：契约文本与提示以绝对路径为准，相对路径保留为兼容分支（按主根解析）。理由：与桌面用户心智一致（工作区面板显示的就是绝对路径），且边界校验点唯一（工具侧 `WorkspacePathResolver` 已在做前缀校验，只需扩展为允许根集合 + 可执行报错）。
- **模型必须知道根路径**：绝对路径契约要求模型知道根，因此阶段 1 的提示注入不是可选装饰而是前置依赖。
- **额外根只读**：多根只扩展读，写永远限定主根，避免"多根写"带来的 grant/回滚/快照复杂度（`GitWorkspaceSnapshotProvider` 只覆盖主根）。
- **`mcp_invoke` 改判 read**：它本质是调用外部 MCP server 的一次调用，风险由 `RequiresApproval` 与审批门控制，不应等同于"改工作区"。这样只读 agent 持有 `read:` grant 时不再莫名 `explicit_deny`。
- **保持 fail-closed**：空 grants 依旧拒绝，`ToolResourceAllowList` 空表语义不回退为 unrestricted；"默认读权"通过准入期**显式写入冻结 grants** 实现（可见、可审计），而不是运行期隐式放行。
- **MCP 定位**：内置 `ls/file_search/read_file` + 只读 git 作为基线，MCP 作为可选扩展；`mcp_search`/`mcp_list` 的空结果与失败都必须带原因。

### 三、性能与可靠性
- 顶层清单在准入时枚举一次并有条数上限与截断标记，不进入每轮 prompt 构建的热路径；提示新增段落消耗 token 但按预算裁剪，且对同一 run 稳定（利于模型侧提示缓存）。
- `ToolResourcePathRegistry` 每次派发多一次小 JSON 解析与路径归一，属既有量级；多根匹配为前缀比较（O(根数)）。
- 保持既有幂等与可恢复纪律：错误 JSON 写入 checkpoint 的任务 turn，续跑不重复派发；不动 lane/tier/`RunFreezeGate` 语义。

### 四、落地注意事项
- 契约三件套 `TinadecGateway/tests/__snapshots__/openapi.core.json`、`openapi.external.json`、`apps/desktop/src/generated/schema.d.ts` 若被牵动，必须同批再生并跑 `npm run check:drift`；本方案尽量把改动收敛在运行时体（工具结果 JSON、提示文本、冻结配置内部段），避免 HTTP 契约漂移。
- `FrozenRunConfigurationV1` 新增段必须 `[JsonIgnore(WhenWritingNull)]` 且只在有项目根时写入；既有 v2 body 反序列化后该段为 null，恢复不失败（沿用 Phase 2"投影容错 vs 恢复门禁"的显式设计）。
- `GraphSeedPack/manifest.json` 改动会变更 pack digest：同步 `graphSeedPackBootstrap` 与其测试、必要时 Core 侧自包含夹具；不要让 Core 测试再依赖桌面产物。
- 不要回退工作树中未提交的 TinadecTools stdin 修复（`TerminalRunner`/`RipgrepRunner`/`WindowsSandboxRunner`/`GitCli`）与 `apps/desktop/src/api.ts` 的错误提取改动。
- 修改代码后按项目纪律同步受影响 `AGENTS.md` 的内容段与元数据；当前无新提交，`Last Verified Commit` 应留到提交时刷新，不得臆造 hash。
- 明确不做：桌面工作区面板与可观测性 UI、`AGENTS.md`/指令文件自动发现、LSP 接入、lane 机制改动（登记为后续批次）。

## 关键数据结构

```csharp
/// 准入期冻结的工作区绑定；null 表示该 run 没有项目根（projectless 会话）。
/// 只在存在项目根时写入，恢复路径缺段即视为无工作区，不新增 schema 门禁。
public sealed record FrozenWorkspaceBinding(
    string RootPath,              // 绝对路径，主根 = 可写根 = TinadecTools 子进程 CWD
    IReadOnlyList<string> ReadOnlyRoots, // 额外只读根（绝对路径），写操作一律不允许
    bool IsGitRepository,
    string? GitBranch,
    IReadOnlyList<string> TopLevelEntries, // 准入期枚举一次，带上限与截断标记
    bool TopLevelTruncated,
    string PathContract);         // 契约标识，如 "absolute-in-root"
```

提示段落形态（`PromptAssembler` 追加，受预算裁剪）：

```text
Workspace: exactly one workspace is in scope for this run.
Root (absolute): <RootPath> [git repository, branch <GitBranch>]
Path contract: every path argument must be an absolute path inside the root;
relative paths resolve against the root. Nothing outside the root is readable or writable.
Extra read-only roots: <...> (omit when empty)
Top-level entries: <...> [truncated]
Do not ask the user for the workspace path; use the root above.
```

## 验证方式
- 单元/集成：提示装配断言 Instructions 含根路径与契约段；冻结配置往返 + 旧 v2 body 缺段恢复不失败；grant 矩阵（只读工具 + read 权 → allowed；mutating + 仅 read → 拒绝且消息含根与缺失级别；mutating + write → 走审批）；路径边界（根内绝对、根外绝对、相对、额外只读根、`..` 与符号链接）。
- 端到端：一次带工具调用的 run 中被拒工具必须让模型收到结构化 Tool 消息；`mcp_search` 无 server 时必须带 `reason`。
- 契约与摘要：`npm run check:drift`（桌面）、pack digest 与 `graphSeedPackBootstrap` 测试、既有 `FullDuplexEndpointTests` 全绿（三档 tier 与 lane 拒止零回归）。


## Agent Extensions
### SubAgent
- **code-explorer**
  - Purpose: 只读复核工作区契约在仓库内的覆盖情况——确认所有需要路径的工具/调用点（`ls`/`stat`/`read_file`/`write_file`/`file_search`/`git_*`/`shell`、`DirectToolEndpoints`、`ToolDispatcher`、`ToolResourcePathRegistry`）都已纳入新契约，且没有遗漏的旁路调用点。
  - Expected outcome: 产出一份"契约覆盖清单 + 遗漏点清单（含文件:行）"，作为实现与验收依据。
