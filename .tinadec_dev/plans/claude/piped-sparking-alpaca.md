# 空间模式优化规划：从卡片画布到集群协作工作台


> 2026-10-07接手：第一阶段产品实现与定向/全量测试已收口到工作树，第二/三阶段及真实模型与平台验收仍待继续。具体证据与边界见[接手报告](../../reports/2026-10-07-space-clusters-handoff.zh-CN.md)，唯一任务状态见[APP-RENDERER-104](../../../docs/development-program/02-modules/app/shared-renderer/TODO.md#app-renderer-104)。原规划中的只读限制属于当时调查轮，用户现已授权继续实施。

## Context

用户希望先理解现有空间画布，再规划控件如何摆放、如何表达信息传递，并借鉴相关项目的视觉语言，体现 TinadecOffice 的集群协作。原规划轮仅完成源码调查、现有 Electron 只读观察、外部参考研究与方案设计，**不修改产品代码、不运行测试、不启停服务、不调用模型**。

**推荐定位：一张围绕目标组织的、可追溯的协作工作台。** 不是把聊天记录拆成卡片，也不是另造工作流编辑器。集群感来自共同目标、分工、真实交接、独立审查与结果收敛，而非大量机器人头像或持续闪烁的连线。

关联既有任务：[APP-RENDERER-104](../../../docs/development-program/02-modules/app/shared-renderer/TODO.md#app-renderer-104)。本方案是该任务的空间表达优化，不代替其中尚未完成的组合执行、完整智能体工作画面和平台验收。

## 1. 现状判断：基础有了，缺的是组织与关系

### 可以保留的基础

- Vue Flow 负责交互，UIE 是几何与布局持久化的唯一入口；已有拖动、缩放、调整尺寸、撤销重做、会话布局隔离。
- 画布透明，工作卡沿用主题材质，Composer 固定；已有快捷预览与定位。
- 已有任务、计划、工具、终端、审批、Git 和组织读模型，不需要重写这些能力。

### 需要优先解决的问题

1. **默认排列不表达协作。** `syncSpace` 目前让新卡以 420px 宽纵向排列；自动卡会随数据顺序和内容高度变化。它表达的是阅读顺序，不是并行分工或前置约束。旧布局和手动位置另行保留。
2. **任务与智能体混在一起。** `projectSpatialObjects` 用 handle/agent 名优先作任务标题，却丢弃了 topology 已有的执行实例、派发者、资源租约等关联字段。
3. **同一种线混合多种含义。** 任务依赖是真实调度约束；会议到工具、Git、审批等线主要是前端组织关系，不能当作实际调用或消息传递。
4. **长正文挤占工作结构。** 会议正文、任务、日志一起展开，难以快速判断目标、责任、阻塞和结果。单会议卡还可能同时呈现旧答案与新运行状态。
5. **数据和操作边界不明显。** 截断、刷新失败、未知归属没有充分表达；空间缺部分队列与监督入口，终端“在功能面板打开”仍指向空间未渲染的右栏。

源码依据：[对象投影](../../../apps/desktop/src/lib/spatialObjects.ts)、[空间页面](../../../apps/desktop/src/pages/SpatialPage.vue)、[UIE 几何](../../../apps/TinadecUI/src/engine/spatial.ts)、[拓扑契约](../../../TinadecCore/Contracts/Dtos/SessionTopologyDtos.cs)。

**观察边界：** 当前 Electron 的 1463×867 视口有 3 张卡、2 条无标签线，缩放约 0.494，两张任务卡接近或超出屏幕底部。这只代表当前会话及其持久布局。截图接口超时，因此没有像素级验收结论；也没有验证新的真实模型链路。

## 2. 推荐空间结构

### 一处会话入口，多个目标工作簇

- **会话入口**：沿用唯一会议身份，承载真实待发送队列、当前目标导航，不再把所有历史答案塞成一份不断增长的正文。
- **目标工作簇**：按一次运行（run）组织输入、任务、结果和数据完整性提示；是视觉分区，不是新业务实体或第二个会议智能体。
- **任务卡**：主标题是“正在做什么”；实例 chip 表达“当前由谁负责”。同一实例可承担多项任务，不按名字合并实例。
- **工作详情**：选中任务或实例后，查看其已加载的计划、公开工作说明、工具、终端、结果、证据和相关关系。
- **项目资源区**：当前 Git、文件、共享资源单独放置。当前工作区状态不能冒充某位执行者或某次历史运行的专属产物。

### 控件之间怎样摆

1. **纵向表达前置关系，横向表达独立分支。** 依赖更深的任务往下排，同层任务横向展开。横向只表示没有已知前置依赖，是否真的同时执行以 Core 状态为准。
2. **结果在目标簇尾部，审查贴近被审查对象。** 只有真实引用或交接记录才能连“成果进入汇总”的线，不能为了构图强行连接全部任务。
3. **默认展开当前目标，其他目标保留摘要与入口。** 不因历史变长就自动缩小整张画布。新目标和新事件不抢走正在阅读的镜头。
4. **任务卡先给摘要。** 新默认建议约 360px 宽、160px 高，展示标题、责任、状态/等待原因、结果入口；具体尺寸在原型验收中校准。全文进详情，旧卡尺寸及展开状态不强制迁移。
5. **位置稳定优先。** 初次自动安放；已有卡不因状态、数组排序或流式文本增长重新移动。新增任务寻找空位；用户主动“整理本目标”才按最新依赖重排。
6. **几何不改变归属。** 拖出分区的任务仍属于原 run，并保留目标标识与定位入口。首版不引入可拖拽嵌套容器，也不让背景为了包住远处卡片无限扩大。

这会将现有“默认单列全文卡”改为“默认目标分区和任务摘要”。它是推荐的新默认，不是对旧布局的强制清理。

## 3. 信息传递：先规定线的含义，再设计线的外观

### 三种表达，而不是一张全连接网络

| 表达 | 含义 | 事实条件 |
|---|---|---|
| 细实线箭头，标“需完成” | 前置任务到后继任务 | 同 run 的真实 dependencies |
| 次级虚线箭头，带具体动词 | “派发”“回执交回”“发布到房间”“针对该任务的报告” | 明确 ID 关联、事件或报告引用 |
| 分区、chip、列表，不画调用线 | run 包含任务、任务绑定实例、项目拥有资源 | 对应归属字段 |

线型区分关系种类，不表达可信度。每条可见关系都要能查看来源；不支持的关系直接不画，不用虚线补猜测。

- 默认只显示主要依赖。选中对象后，显示其直接相关的协作关系；全局关系筛选明确当前范围。
- 点击线或关系条目，显示两端对象、关系类型、来源字段/事件、可用载荷，以及发生时间；只有快照时间时标“获取时间”。
- 有内容时展示“交接了什么”，例如任务简报或结果摘要。不能只给一个光点动画，却没有可以回查的内容。
- 关系同时提供文字列表和键盘入口，不能只靠鼠标命中细线。
- 采用现有主题色与状态 token；状态始终有文字/图标，不用一套身份彩虹。第一版不增加持续飞线动画。

### 必须守住的语义边界

- **依赖完成不等于结果已传入下游。** dependencies 证明调度前置约束，不证明数据载荷传递。
- **任务完成不等于父智能体已收到或理解。** `task.wait_resolved` 可证明 Core 把回执交回父任务工具轮，仍不能证明模型理解或采用。
- **创建血缘和模式允许关系不是实际通信。** 两者不进入默认信息流图。
- **组织帖子只展示有记录的 sender → room/post。** 当前公开投影没有完整收件人和回应链，不能画成已确认的一对一交流。
- **报告“已处理”不等于建议已执行。** 必须有实际控制动作回执，才能声称执行了暂停、改派等操作。
- **公开推理不是内部思维全集。** 展示计划、公开说明、结果和证据；无数据就说明没有可用记录，不补造思考过程。

## 4. 阅读和操作路径

**远景 → 中景 → 详情** 是最终阅读层级，首版用显式展开完成，不把语义缩放作为前置条件。

- 远景：目标、状态、已加载任务概况和需要介入的位置。
- 中景：任务分支、当前责任与主要依赖。
- 详情：具体工具、终端、审批依据、结果和公开记录；实例视角汇集该实例已加载的任务，而不是复制所有卡。

重要情境：

1. **待发送/已提交**：只有 controller 的真实队列叫“待发送”；提交后关联目标。无 run 的历史消息显示未关联，不一律标排队中。
2. **等待/失败**：明确区分等待前置、等待审批、运行失败、数据加载失败。无法确认阻塞原因时不推测。
3. **审批/监督**：先核对 session/run/subject，再复用现有裁决入口；几何选择不改变权限。屏幕边缘可以提示有待处理工作，但不自动拉镜头。
4. **收尾/重入**：答案归对应 run，多 run 的回复不串接；保留失败、取消和部分结果。历史视图称“当前可用记录”，不提供未经支持的任意时间滑块。
5. **刷新/断线**：保留最近成功投影并标过期；显示已加载量、截断和错误。没加载到不是没发生过。
6. **工作详情宿主**：在空间中提供可见的按需详情面，复用现有组件，不重建第二套面板状态系统。终端打开动作必须指向可见宿主。已打开的终端不因折叠、离屏或切换焦点而被销毁；切会话时仍严格隔离。

定位与总览需避让固定 Composer 和已打开的详情面。旧布局恢复优先，不在进入空间时偷偷 fit 全图。

## 6. 实施路线与文件边界

### 第一阶段：让集群工作看得懂

交付目标：新会话按目标组织任务，用户能直接辨认分工、责任、依赖、阻塞和结果入口；旧布局保持可用。

1. **先调整投影语义。** 在 `projectSpatialObjects` 保留稳定 ID，补 run/task/instance 引用和独立关系集合；展示归属从 `parentIds` 的依赖含义中分离。任务使用工作标题，实例作为责任 chip。答案按 run 归位，未知归属计划/工具留在 run 级列表。来自旧 orchestration fallback 的记录也要核对其归属，不把缺字段当已确认关联。
2. **再调整 UIE 安放。** 扩展 `SpatialSeed` 的最小布局提示，复用 `syncSpace`、`moveSpace`、`repairSpace`。按真实依赖稳定拓扑分层，同层以稳定 ID 排序；首次安放与显式整理共享纯布局函数。增量只安放新节点，旧坐标保留，简单矩形避让即可。
3. **处理异常图。** 未解析依赖保留诊断；拓扑未消解的节点放入待核验区，不把所有剩余节点一律称为环。消息、回执和反馈边不参加依赖分层。
4. **实现呈现与定位。** run 分区、任务摘要、实例聚焦、关系标签/列表、空间可见详情、失败/截断提示；复用现有 `loadTopology` 的 generation/abort、`commit`、`locate`、`overview`，不新增业务 store。
5. **保留兼容性。** 旧 ID、位置、尺寸和已展开工作控件保留；新摘要不删除已有几何。目标背景由当前呈现派生，不成为第二份布局权威。必要的显示偏好仍走现有会话 UIE 存储。
6. **整理可撤销。** “整理本目标”明确会移动该目标内包括手动摆放的卡，执行一次批量 `spaceMove`。复用 command bus 的按受影响对象恢复，不整份回滚空间；当前镜头、其他 run 与随后新增节点都应保留。
7. **补齐基本入口。** 队列编辑/取消、监督与审批导航、空间可见终端入口；不改既有批准/拒绝、停止/继续的业务语义。

- `apps/desktop/src/lib/spatialObjects.ts`、`spatialObjects.test.ts`
- `apps/desktop/src/pages/SpatialPage.vue`；新增 `SpatialPage.test.ts`
- `apps/desktop/src/components/spatial/SpatialWorkCard.vue`；新增同名测试，必要时提取一个空间详情组件
- `apps/TinadecUI/src/engine/spatial.ts`、`spatial.test.ts`；类型/序列化沿既有 UIE 导出和修复路径同步
- `apps/desktop/src/controllers/HomeController.ts`、`composables/useAgentActivity.ts`：仅补充必要的逐 run 读取与既有动作暴露，不复制控制器
- `apps/desktop/src/locales/`：现有双语文案文件

优先复用：`ToolCallCard.vue`、`TerminalCallBlock.vue`、`TurnTimeline.vue`、`ApprovalCard.vue` → `ApprovalTab.vue`、`OrganizationPanel.vue` 的事实读取、`useSpatialGit`、`sessionEventBus`、Composer 队列 controller。复用行为，不把整块复杂面板直接复制进每个节点。

**这一阶段不包含**：后端重构、全组织通信图、任意时点回放、force 布局、ELK 等新依赖、语义缩放或离屏卸载。

### 第二阶段：让交接与证据查得实

- 先把现有工具执行的 task/instance/step-result 归属公开到工具时间线和前端活动模型，缺值保持 unknown，不为界面另建一套完整事件重构系统。
- 使用已记录的派发、回执、报告、房间帖子建立可回查的关联；有明确关联才开放成果引用、接续等关系。
- 依据真实资源租约展示占用；任务的写入范围不等于它实际修改的文件，Git 当前更改也不等于历史产物。
- 接通按证据定位的审批/监督，以及既有 parallel/insert 队列高级操作；范围检查仍由 Core 保持权威。
- 若增加 DTO 字段，修改 `TinadecCore/AspNetCore/Endpoints/DmaeaEndpoints.cs` 的现有时间线投影及对应契约，Gateway 保持薄代理；同步外部 OpenAPI、生成客户端与 `api.ts`、`useAgentActivity.ts`，不手改生成文件。
- 读面调查发现的过滤/游标问题先定向回归确认。相关路径未证明完整前，UI 保持有界/未知提示；不能把一次空间改版膨胀为全部 runtime 缺口的重写。

### 第三阶段：规模与平台

- 在第一阶段结构稳定后，增加一跳/两跳和方向筛选、语义缩放、大量历史目标的按需加载。
- 测量轻量节点与重控件的渲染/内存，再决定裁剪、布局库或分层渲染；不能直接开启离屏卸载破坏终端与编辑器。
- Web 当前生产路径缺布局桥，作为明确的平台缺口处理，不宣称已有 Electron 同等持久化。
- 完整分页、跨流 cursor、watermark、历史 `as_of` 分别按 Core 契约规划。普通 task_dispatch 目前仍在同 run 中生成任务，不用视觉嵌套冒充独立子 run。

## 7. 验证与验收

### 真实界面

通过已批准的 preview 启动配置运行前端，使用 snapshot、console/network、inspect、click/fill、resize、screenshot 验证；Electron 原生布局恢复与终端桥再用 Electron MCP 补充，不能用浏览器结果代替原生持久化结论。

1. **标准三任务场景**：1463×867 下两条独立分支与一个后继任务可读，目标、责任、等待原因和结果入口不必滚动长日志才能找到。900/1120 宽度下主操作不被详情或 Composer 遮挡。
2. **稳定性**：连续流式文本、任务状态改变、拓扑数组乱序不移动现有卡或镜头；新增对象不压住已有摘要卡。
3. **真实性**：依赖完成不产生伪消息，普通 completed 不标回执，房间帖子不画私信，未知 owner 不绑定 worker。
4. **可操作性**：导航定位避让覆盖层，队列、审批、监督与终端入口可使用；布局行为不改变业务权限或执行方式。
5. **可恢复性**：Electron 切会话、刷新和重入恢复旧布局；Web 明确说明当前持久化能力边界。
6. **可访问性**：深浅主题、三种材质、键盘焦点、文字/图标状态、关系列表、减少动态效果；不只依赖颜色和细线。
7. **规模证据**：分别测量少量、数十、数百轻量任务节点及重控件开启后的交互，记录数量/耗时/内存，不把小图通过写成无限历史可用。
8. **业务证据单列**：受控夹具证明 UI，不证明模型协作。第二阶段需在隔离演练项目以实际 Gateway/Core/模型链验证分工、审批、结果返回；缺少环境或授权时明确未验收，不修改用户模型路由来凑结果。

## 推荐结论

**先做“目标工作簇 + 稳定分支布局 + 有语义的关系 + 按需工作详情”。** 这是让空间真正区别于平面聊天的最小完整切片。再用真实回执和证据逐步补齐协作表达，最后才投入语义缩放与大规模历史。保留 Vue Flow、UIE、主题材质和既有治理链路，不把视觉优化变成另一套运行系统。
