# issue #30 / #33 / #34 修复报告（2026-10-08）

对 GitHub 上外部贡献者提交的 `#30`–`#34` 复核后，`#31`/`#32`（工具层）当时已由本仓自行修复，
本轮修掉剩下三个。**本文只记录实际核查与改动，不复述 issue 原文结论**；其中 `#30` 的
头号指控经核查在本仓当前依赖版本上**不成立**，下面单独说明。

## 一、#30 gateway：结论与 issue 描述不同

### 复核：issue 的头号指控复现不了

issue 称 `onError` 未赋值 `set.status`，导致"路由已暂存 2xx 后出错 → 返回 HTTP 201 + 错误体"的假成功。
在当前依赖（`elysia@1.4.29`）上**不成立**：

```js
// node_modules/elysia/dist/compose.js:917（路由 handler 的 catch 内）
if(!set.status||set.status<300)set.status=error?.status||500
```

Elysia 自己就把暂存的 2xx/3xx 钳成了 500，4xx/5xx 才保留。实测（探针 + 用例）：

| 场景 | onError 里看到的 `set.status` | 实际响应 |
| --- | --- | --- |
| 路由 `set.status = 201` 后抛 `new Error` | 500 | 500 |
| 路由 `set.status = 201` 后抛 `s[429]` | 500 | 500 |
| 附件路由暂存 201 后 `response.json()` 解析失败（issue 的复现场景） | 500 | **500 + ProblemDetails**，不是 201 |

即：**"失败被伪装成 2xx"在本版本不可复现**。原先那行 `const status = typeof set.status === 'number' ? set.status : 500;`
因为 Elysia 已经钳过，恰好等价于"只继承 4xx/5xx"，是**侥幸正确**而非按契约正确。

### 真正修掉的是什么

裸 `fetch` 路径的异常逃逸进 catch-all，客户端收到 **500** 而不是 **502**——
分不清"网关自己坏了"和"上游没起来"。这条是实打实的缺陷，也正是 `serviceDiscovery` 那类探针
需要区分的指纹。

改动：

- 新增 `TinadecGateway/src/upstreamFailure.ts`：统一的 502 ProblemDetails 构造。刻意不走
  `toProblemDetails`，因为 `normalizeCode` 会把未知 code 重写成 `conflict`，抹掉
  `CORE_UNREACHABLE` / `TOOL_RUNTIME_UNREACHABLE` 这个指纹。
- 六条裸 `fetch` 全部加兜底：`coreClient.proxySse` / `proxySseWithCursor` / `proxyStream`、
  `streaming.proxyStream`、`toolRuntimeClient.proxyToolRuntimeSse` / `proxyToolRuntimeStream`。
- `index.ts` 的 catch-all 显式 `set.status`，并把"只继承 4xx/5xx"写成明示契约（附 Elysia 版本行为注释）。
- `config.ts` 标注 `TINADEC_GATEWAY_TIMEOUT_MS` **当前无人消费**。它仍是死配置：给所有上游
  fetch 加 `AbortSignal` 必须放行 SSE/流式（它们本来就要长开），那是行为变更不是缺陷修复，
  与 issue 作者自己的 PR 结论一致，留作独立项。

### 测试

`src/errorStatus.test.ts`（4 条）：

- 2 条 **lock-in**：暂存 201 → 500、暂存 413 → 413。它们修复前后都过，作用是钉住 Elysia 的钳制行为，
  注释里写明"这不是修复前会失败的复现用例"，避免后人误读成回归覆盖。
- 2 条**真回归**：Core 不可达时 SSE 路由 / 流式下载必须 502。
- **变异验证**：让 `upstreamUnreachableResponse` 改回抛错 → 这 2 条正好退化成 `actual: 500, expected: 502` 失败。

网关全量：**84 pass / 0 fail**（改前 80），openapi 快照无变更。

## 二、#33 desktop 安全

issue 的三条主诉全部成立并已修复；"连带发现"里**一条不成立**：

- **不成立**：CORS `ALLOWED_ORIGINS` 里的 `'file://'` 并不会让任意本地 HTML 调网关。
  `isOriginAllowed` 是字符串全等/正则匹配，而 file:// 文档发出的 `Origin` 字面量是 `null`，
  两边都不匹配 —— 那是**死条目**，不是漏洞（issue 作者自己标了"需要核实"）。已删除该条目，
  并换成打包态真实使用的 `app://bundle`。

修复内容：

1. **恢复同源策略**：四个窗口（`main.cjs` / `panelWindow.cjs` / `petWindow.cjs` / `debug-studio.cjs`）
   移除 `webSecurity: false`。打包态不再 `loadFile`，改由新增的 `app://bundle` 标准 scheme
   （`electron/appBundle.cjs`）承载 `dist/`，带真实 origin、路径穿越防护、MIME 映射、`/` → `index.html`。
2. **本地媒体改走自定义 scheme**（`electron/localMedia.cjs`）：这是 `file:///` 停止可用之后的替代路径。
   只服务图片/视频扩展名、只服务存在的普通文件、支持 Range（`<video>` seek）、**不发 CORS 头**
   （异源 `fetch()` 读不到字节，而 `<img>`/`<video>`/CSS 仍可加载）。
   残留能力已在文件头写明：渲染层仍可点名任意媒体扩展名路径，与 `tinadec:read-image-data-url`
   同级；进一步收紧（只放行文件对话框授权过的文件）需要渲染层启动时回环，属产品决策。
3. **终端 IPC 白名单化**（`electron/terminalManager.cjs`）：
   - `terminal:create` 只接受 shell 目录内的条目，**argv 一律取目录值**（接受白名单 shell 却仍用调用方
     argv 等于没修）；未知 shell 直接拒绝且不 spawn；
   - **id 一律服务端生成**（客户端 id 可覆盖活条目、孤儿化 PTY）；
   - `write`/`resize`/`destroy`/`snapshot` 校验 `event.sender` 是否为该终端 owner。
4. **外链修复**（`electron/externalLinks.cjs`）：`setWindowOpenHandler` 由"一律 deny"改为
   deny + `shell.openExternal`（仅 http/https），并补 `will-navigate` 处理正文里的普通链接点击
   （同源导航放行，hash 路由不受影响）。
5. **启动健壮性**：`probeWsl()` 的 `execFile` 是同步抛出的（缺 wsl.exe / 被执行策略或 AV 拦下时），
   它跑在 register 启动路径上，会把整个主进程带走 —— 已加 try/catch。
