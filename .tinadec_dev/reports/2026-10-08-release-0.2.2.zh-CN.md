## 阻塞点与诊断（有读数）

0.2.2 起初发不出来，因为 `release` 需要三条腿的产物，而 mac 腿在 `vite build` 里 OOM：

- `37678073211`（`ed12133`）`Build osx-arm64` 的失败步骤是 `Build and package the application`，日志为 `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory`，堆停在 ~2040 MB，`Abort trap: 6`，npm 退出码 134。
- 更早就红的 mac 腿（`37645643134` / `37675656686`）失败在 `Typecheck Desktop`（`SpatialPage.vue` 的 TS2345），与内存无关，且已在 `ed12133` 修掉；正因如此 `ed12133` 是 Markdown 那批依赖进来后**第一次真正跑到打包步骤**的提交。
- `v0.2.1` 的 `86aeff6` 那次 mac 腿是 success，说明默认堆顶当时够用。因此这是 bundle 长大撞上较小的默认堆顶，不是 macOS runner 抖动。
- 本机（Windows）A/B 复现同一失败形状：同一份 `vite build`，`--max-old-space-size=2048` → 退出 134、堆 ~2034 MB、同一条 `Ineffective mark-compacts` 报错；`--max-old-space-size=8192` → 退出 0，`✓ built in 4m 59s`。

处置：`eac73f1` 只给 `osx-arm64` 这条 matrix 腿加 `nodeOptions: --max-old-space-size=8192`，由 `Build and package the application` 步骤以 `env: NODE_OPTIONS: ${{ matrix.nodeOptions }}` 注入。另两条腿没有该键，`NODE_OPTIONS` 取到空串，实测 Node 接受空 `NODE_OPTIONS` 且不改变行为。工作流 YAML 用 `js-yaml`（CORE_SCHEMA）解析核对过三条腿的取值与步骤 env。

**这不是修复，只是把天花板抬到够用。** 真正该做的缩小 bundle 没做：产物侧证据是 `editor.main-*.js` 单块 3 774 kB（gzip 974 kB），vite 自己仍在提示 “Some chunks are larger than 500 kB after minification”，说明 Mermaid / Monaco / KaTeX / highlight.js 这些大件基本没有按需切分。

## 资产一致性核验

- `SHA256SUMS` 22 行；按 basename 归一后与 release 里除 `SHA256SUMS` 自身的 22 个资产集合完全相等（对称差为空）。注意 sums 里记录的是打包暂存目录路径（`./office-channel/...`），而资产是平铺上传的，比对必须先取 basename——直接按整行名字比会得出“一个都对不上”的假读数。
- 实际下载并重算校验了 7 个小件（4 份 catalog + 3 份 agentpack）：`sha256sum -c` 全部 OK。三个安装包（deb 212 MB、dmg 234 MB、win setup 261 MB）没有重新下载校验，只核对了存在性与大小。

## 已知边界（不可当作已验证）

- **未签名**：工作流全局 `CSC_IDENTITY_AUTO_DISCOVERY: 'false'`，Windows NSIS 与 macOS 包都是无签名产物，macOS 未走公证；这与 0.2.1 及之前一致，不是本次引入。
- **POSIX Core 主干是红的**：`posix-core.yml` 在 `2cc7b15`（即 tag 所在树）ubuntu/macos 两条腿都 failure，失败用例为 `AgentPackEndpointTests.AgentPackLifecycle_AgentModeSelectsPublishedConversationModeVersion`、`CliDiscoveryTests.DiscoverHarnesses_StatesEachChannelAndWhatThisBuildCanDrive`、`ToolChainEndpointTests.AskMode_RunsOnNarrowedRoster_BrowserWorkerCompletesWithoutSupervisor`、`UnattendedEndToEndTests.PreAuthorization_EndToEnd_GitCommitWithoutHuman`、`PosixSandboxIntegrationTests.AWriteOutsideEveryGrantedDirectoryIsDeniedByTheKernel`、`PosixSandboxIntegrationTests.TheChildSeesTheRetainedEnvironmentAndNothingElse`、`PtyBackendContractTests.Start_RejectsAScreenTooSmallToHoldAPrompt`。`ed12133` 同样两腿全红，所以不是 0.2.2 引入的。要点是 `desktop-release.yml` 根本没有任何 Core 测试步骤，所以 Core 产物（`tinadec-office-core-0.2.2-*`）是在这条红线之上打包发布的——这是发布流水线的门禁缺口，不是本次改动的回归。
- 其中 `PosixSandboxIntegrationTests.AWriteOutsideEveryGrantedDirectoryIsDeniedByTheKernel` 的失败读数值得单独查：子进程 `exit=0 stdout=started`、`stderr` 与 `error` 均空、`fileNowExists=False`，即“越界写没落盘，但命令也没报错”，这与该测试设计要给出的“内核拒绝”证据形状不一致；本轮只登记，未定因。
- 真实外部模型、PostgreSQL、带旧布局文件的真实用户库升级路径本轮均未演练。
- 发布说明是 `gh release create --generate-notes` 自动生成的，正文只有 PR #29 与 compare 链接；`v0.2.1` 的正文只有一行 compare 链接。仓库没有 `release-notes/` 目录，`docs/tinadec-office-release-contract.zh-CN.md` 也没有对发布说明提出要求，所以这里只登记现状，不把它当成本次的交付缺口。
